# OURVERSE 3.0 고객 페르소나 및 사용자 여정

- WBS: 1.1.2
- 작성일: 2026-11-24
- 서비스: OURVERSE 3.0 / TWO-PICK
- 근거 문서: `MVP_SCOPE.md`, `FEATURE_SPEC.md`, `API_CONTRACT.md`, `SYSTEM_ARCHITECTURE.md`, `DB_DESIGN.md`

## 문서의 검증 수준

이 문서는 서비스 기획을 위한 **가상 페르소나와 사용자 문제 가설**을 정의한다. 실제 커플 인터뷰, 관찰 조사 또는 사용성 테스트 결과가 아니다.

문서에서는 다음 세 종류의 정보를 구분한다.

- **확정된 기획 범위:** 프로젝트가 대상으로 삼기로 결정한 사용자와 P0/P1/P2 범위
- **기획 가설:** 실제 사용자가 그 문제를 경험하는지 향후 검증해야 하는 추정
- **현재 구현 상태:** 현재 `main`의 코드와 연결 상태를 기준으로 한 기술적 판정

사용자 여정 표의 구현 상태는 다음 기준을 사용한다.

- **implemented:** 현재 웹 UI와 백엔드가 연결되어 사용자가 해당 단계를 수행할 수 있음
- **partial:** 일부 코드 또는 백엔드 API는 있으나 UI 연결, 영속 기록, 동시성 보장 등 여정 완성 요소가 부족함
- **planned:** 현재 모델, API 또는 UI가 없으며 기획만 존재함

이 구현 상태는 사용성이나 사용자 가치가 검증됐다는 뜻이 아니다.

## 1. 타깃 사용자 정의

### 현재 확정된 서비스 타깃

OURVERSE 3.0의 기획상 핵심 타깃은 다음 상황에 있는 연인 또는 부부다.

- 데이트 장소, 식사, 일정, 선물 등 둘이 함께 결정해야 하는 상황이 반복됨
- 두 사람이 각각 독립 계정을 사용할 수 있음
- 취향, 예산, 시간 또는 우선순위가 달라 결정에 조율이 필요할 수 있음
- 한 사람의 일방적 선택이 아니라 두 사람의 명시적인 합의를 원함

이는 **프로젝트가 선택한 목표 사용자 정의**이며, 실제 시장 규모나 문제 빈도를 사용자 조사로 입증했다는 의미는 아니다.

### 아직 검증되지 않은 타깃 가설

다음 내용은 실제 사용자 조사 전의 가설이다.

- 공동결정 상황이 충분히 자주 발생해 별도 서비스를 사용할 가능성이 있다.
- 두 사람이 각자 조건을 입력하는 방식이 직접 대화보다 편할 수 있다.
- “동일한 최신 후보에 대한 양측 승인”이 합의의 모호함을 줄일 수 있다.
- 결정 기록과 OUR PET 보상이 재사용 동기를 높일 수 있다.
- 하드웨어 없이 웹만으로도 핵심 가치를 느낄 수 있다.

## 2. 가상 페르소나

아래 두 사용자는 실제 인물이나 조사 참여자가 아닌 **가상 페르소나 한 쌍**이다. 행동과 기대는 제품 흐름을 검토하기 위한 가정이며 실제 사용자 특성으로 일반화하지 않는다.

### 가상 사용자 A

- **관계에서의 역할/성향:** 함께 할 활동의 후보를 먼저 찾아보는 편이라고 가정한다.
- **공동결정 시 중요하게 보는 조건:** 이동 시간, 예약 가능 시간, 전체 일정과의 연결
- **현재 불편 가설:** 매번 여러 후보를 찾고 상대의 반응을 다시 확인하는 일이 부담이 될 수 있다.
- **TWO-PICK에서 기대하는 점:** 두 사람의 조건을 한 흐름에서 반영하고, 상대가 어떤 최신 후보에 동의했는지 명확히 확인하는 것

### 가상 사용자 B

- **관계에서의 역할/성향:** 후보를 직접 많이 찾기보다 제시된 선택지를 비교하는 편이라고 가정한다.
- **공동결정 시 중요하게 보는 조건:** 예산, 음식·장소 취향, 개인 일정
- **현재 불편 가설:** 거절이나 예산 조건을 직접 반복해서 설명하는 것이 부담스러울 수 있다.
- **TWO-PICK에서 기대하는 점:** 세부 조건을 상대에게 그대로 공개하지 않고 반영하며, 자신이 직접 로그인해 최종 후보를 승인하는 것

### 페르소나 관계 가설

- A가 항상 결정권자이고 B가 수동적인 사용자라는 뜻이 아니다.
- 결정 주제에 따라 후보를 먼저 찾는 역할과 중요 조건은 서로 바뀔 수 있다.
- 서비스는 어느 한 사용자의 승인을 대신하거나 두 사람의 권한을 다르게 두지 않는다.
- 두 계정은 동일한 current 후보에 각각 독립적으로 승인해야 한다.

## 3. 핵심 사용자 문제 가설

아래 항목은 **실사용자 검증 전 기획 가설**이다. 현재 문서와 서비스 구조를 설계하기 위한 문제 후보이며 실제 사용자에게 공통으로 발생한다고 단정하지 않는다.

| ID | 문제 가설 | TWO-PICK의 대응 가설 | 향후 확인할 근거 |
|---|---|---|---|
| H1 | 한 사람이 후보를 계속 찾는 부담이 발생할 수 있다. | 두 사람의 조건을 모아 후보 생성·변경 과정을 공유하면 탐색 부담을 나눌 수 있다. | 후보 탐색 담당, 소요 시간, 반복 빈도 |
| H2 | 상대방에게 예산·취향 등 세부 조건을 직접 말하기 불편한 경우가 있을 수 있다. | 사용자별 비공개 조건을 보호하면서 후보에 반영하면 부담을 줄일 수 있다. | 조건 공개 선호, 비공개 기능 신뢰도 |
| H3 | 서로 승인했다고 생각해도 최종 합의가 명확하지 않을 수 있다. | 각 계정의 독립 승인과 `confirmed` 상태가 합의 시점을 명확히 할 수 있다. | 승인 규칙 이해도, 확정 상태 인지율 |
| H4 | 후보가 변경됐는데 과거 동의를 그대로 적용하면 갈등이 생길 수 있다. | 후보별 version과 current 규칙으로 과거 승인을 새 후보에 승계하지 않는다. | 버전 차이 인지, 재승인 수용도 |
| H5 | 결정 과정을 기록하면 이후 선택에 도움이 될 가능성이 있다. | 결정 목록·상세와 향후 최종 결정 기록이 재선택을 도울 수 있다. | 기록 재조회 의향, 필요한 기록 항목 |

## 4. TWO-PICK 핵심 사용자 여정

현재 P0 목표 흐름을 기준으로 작성했다. `partial`은 backend 기능이 있더라도 현재 웹 UI에서 해당 단계를 끝까지 수행할 수 없음을 포함한다.

| 단계 | 사용자 행동 | 시스템 반응 | 사용자 기대 | 현재 구현 상태 |
|---|---|---|---|---|
| 1. 회원가입 | A와 B가 각자 이메일, 닉네임, 비밀번호를 입력한다. | 각각의 User를 만들고 사용자 정보를 반환한다. | 두 사람의 계정이 분리되어 생성된다. | implemented |
| 2. 각자 로그인 | 각 사용자가 자신의 이메일과 비밀번호로 로그인한다. | 각 계정에 별도 JWT를 발급하고 세션을 복원한다. | 내 행동과 상대의 행동이 구분된다. | implemented |
| 3. 초대 코드 생성 | 한 사용자가 커플 공간 생성을 선택한다. | Couple을 만들고 8자리 초대 코드를 반환하며 생성자를 첫 구성원으로 연결한다. | 상대에게 전달할 코드를 확인한다. | implemented |
| 4. 코드로 참여 | 상대가 자신의 계정에서 초대 코드를 입력한다. | 코드를 조회하고 정원이 남아 있으면 같은 Couple에 연결한다. | 두 계정이 하나의 커플 공간에 속한다. | implemented |
| 5. 커플 연결 확인 | 두 사용자가 연결 상태와 구성원을 확인한다. | `/couples/me`로 현재 커플과 구성원을 반환한다. | 올바른 상대와 연결됐음을 확인한다. | implemented |
| 6. 공동결정 시작 | 한 사용자가 결정 주제와 제목을 입력한다. | `open` 상태 Decision을 현재 커플 소유로 생성한다. | 함께 결정할 주제가 공유된다. | partial — backend 구현, 현재 UI 미연결 |
| 7. 각자 조건 입력 | A와 B가 취향, 예산, 시간 등 자신의 조건을 입력한다. | 조건을 사용자별로 저장하고 세부 조건을 상대에게 노출하지 않는다. | 조건은 반영되지만 원치 않는 세부 내용은 보호된다. | partial — 모델·API·자동 테스트 구현, UI 없음 |
| 8. 후보 확인 | 두 사람의 조건을 반영한 후보를 확인한다. | 추천 또는 생성된 current Candidate와 version을 표시한다. | 어떤 조건의 결과인지 이해하고 비교한다. | partial — Candidate 수동 생성·상세 API만 존재, 추천·UI 없음 |
| 9. 필요 시 후보 변경 | 조건이나 의견을 반영해 새 후보를 요청한다. | 이전 후보를 non-current로 바꾸고 version을 1 증가시킨다. | 최신 후보와 이전 후보가 구분된다. | partial — backend 버전 처리 존재, UI·동시성 보강 없음 |
| 10. 최신 후보 독립 승인 | A와 B가 각자의 로그인 세션에서 동일한 current 후보를 승인한다. | 사용자별 DecisionApproval을 저장하고 구버전·중복 승인을 차단한다. | 상대를 대신하지 않고 내 의사를 직접 표시한다. | partial — backend 구현, 현재 UI 미연결 |
| 11. 양측 승인 완료 | 두 번째 사용자가 아직 승인하지 않았다면 기다리고, 승인 후 상태를 갱신한다. | 상세 조회에서 구성원별 승인 상태와 `approval_count`를 반환한다. | 누가 아직 응답하지 않았는지 알 수 있다. | partial — backend 상태 조회 존재, 현재 UI 미연결 |
| 12. 최종 결정 확정 | 두 사용자가 동일한 최신 후보에 승인 완료한다. | Decision `status`를 `confirmed`로 변경하고 추가 후보·승인을 막는다. | 최종 합의가 명확하게 표시된다. | partial — 순차 backend 흐름 구현, UI·동시성 보강·별도 최종 기록 없음 |
| 13. 결정 기록 확인 | 완료된 결정의 목록과 상세 결과를 다시 확인한다. | 커플별 Decision 목록과 current 후보·승인 상태를 반환한다. | 과거 결정을 나중에 다시 볼 수 있다. | partial — 조회 API 존재, UI 및 불변 최종 기록 없음 |
| 14. OUR PET·CARE 연결 | 결정 완료에 따른 펫 성장과 향후 일정을 확인한다. | 경험치 중복 없이 지급하고 일정·알림을 커플 단위로 연결한다. | 결정 경험이 재미와 후속 행동으로 이어진다. | planned — 모델·API·UI 없음 |

### 현재 가능한 웹 여정

현재 `main`의 웹 UI에서 가능한 범위는 다음과 같다.

```text
회원가입 → 로그인 → 초대 코드 생성/참여 → 커플 연결 확인 → 로그아웃
```

Decision, Candidate, 승인과 개인별 비공개 조건 backend API는 존재하지만 현재 프론트엔드에서 호출하지 않는다. 조건 기반 추천, 별도 최종 결정 기록, OUR PET 경험치, CARE 일정·알림은 아직 구현되지 않았다. 따라서 P0 전체 흐름을 실제 웹에서 끝까지 시연할 수 있는 상태는 아니다.

## 5. 실패/예외 사용자 여정

| 상황 | 사용자 경험 | 현재 시스템 반응 | 기대하는 복구 경로 | 상태 |
|---|---|---|---|---|
| 로그인 실패 | 이메일 또는 비밀번호가 맞지 않는다. | 401 `Incorrect email or password`, 프론트가 한국어 오류 표시 | 입력을 확인하고 다시 로그인 | implemented |
| 이미 커플에 가입된 사용자 | 새 커플 생성 또는 다른 코드 참여를 시도한다. | 409 `User already belongs to a couple` | 현재 커플 상태로 돌아가도록 안내 | implemented |
| 잘못된 초대 코드 | 존재하지 않는 코드를 입력한다. | 404 `Invite code not found` | 코드를 확인해 다시 입력 | implemented |
| 커플 정원 초과 | 이미 두 명인 커플 코드로 참여한다. | 409 `Couple already has two members` | 올바른 코드인지 확인하고 참여 중단 | implemented |
| 커플 미가입 상태에서 공동결정 접근 | 연결 전에 Decision 생성·목록·상세에 접근한다. | 409 `User does not belong to a couple` | 먼저 커플 연결 단계로 이동 | partial — backend 처리, Decision UI 없음 |
| 상대 커플의 Decision 접근 | URL의 Decision ID를 다른 커플 ID로 변경한다. | 403 `You cannot access this decision` | 접근을 중단하고 내 커플 목록으로 이동 | partial — backend 구현·일부 테스트, UI 없음 |
| 존재하지 않는 Decision | 삭제됐거나 잘못된 ID를 조회한다. | 404 `Decision not found` | 목록을 새로고침하고 유효한 Decision 선택 | partial — backend 구현, UI 없음 |
| 후보가 아직 없음 | Decision 상세를 열었지만 Candidate가 없다. | `current_candidate=null`, `confirmed=false` | 후보 생성 또는 추천 단계 안내 | partial — backend 응답, UI·추천 없음 |
| 구버전 후보 승인 | 새 버전이 나온 뒤 이전 후보를 승인한다. | 409 `Only the current candidate can be approved` | 최신 상세를 다시 불러오고 current 후보 검토 | partial — backend 구현, UI·직접 자동 테스트 없음 |
| 같은 후보 중복 승인 | 같은 계정이 승인 버튼을 다시 누른다. | 409 `User already approved this candidate` | 이미 승인됨을 표시하고 상세 상태 갱신 | partial — backend 순차 처리, UI·동시성 테스트 없음 |
| 확정 후 추가 승인 | confirmed 상태에서 다시 승인한다. | 409 `Decision is already closed` | 확정 결과 화면으로 이동 | partial — backend 구현, UI·직접 자동 테스트 없음 |
| 한쪽 사용자가 아직 응답하지 않음 | 한 명만 승인한 뒤 기다린다. | 상세 응답에 `approval_count=1`과 사용자별 승인 상태를 반환 | 미응답 상태를 명확히 표시하고 강제 확정하지 않음 | partial — backend 조회, UI 없음 |
| PET DOCK이 연결되지 않음 | 장치 없이 TWO-PICK을 사용한다. | 핵심 API는 하드웨어와 독립적으로 동작한다. PET DOCK 기능은 제공되지 않는다. | 웹의 로그인·조건·후보·승인·확정 흐름을 계속 사용 | partial — 독립 구조는 확정, P0 웹 전체와 PET 통합은 미완료 |

### 하드웨어 예외 원칙

- PET DOCK 연결 여부는 로그인, 커플 연결, Decision, Candidate 또는 승인 권한에 영향을 주지 않는다.
- Arduino 버튼과 BLE 이벤트는 `/candidates/{candidate_id}/approve`를 호출하지 않는다.
- 공동결정 승인은 로그인한 두 사용자가 웹에서 각각 수행한다.
- 하드웨어 장애는 PET 관련 피드백만 제한해야 하며 TWO-PICK P0 흐름을 중단시키지 않아야 한다.

## 6. 향후 검증 — 실제 사용자 테스트에서 확인할 가설

아래는 **향후 검증 질문**이다. 아직 인터뷰, 사용성 테스트, 정량 측정 결과가 없으므로 통과 여부나 사용자 반응을 기록하지 않는다.

### 시작과 연결

- 공동결정 시작 방법을 설명 없이 이해할 수 있는가?
- 회원가입과 두 개의 독립 계정 사용 이유를 이해하는가?
- 커플 초대·연결 과정이 어렵지 않은가?
- 같은 브라우저 또는 서로 다른 기기에서 두 계정을 사용하는 방법이 명확한가?

### 조건과 후보

- 개인 조건 입력을 부담 없이 사용할 수 있는가?
- 어떤 조건이 상대에게 공개되고 어떤 조건이 비공개인지 이해하는가?
- 생성된 후보가 두 사람의 조건을 반영했다고 신뢰하는가?
- 최신 후보와 이전 후보의 차이를 이해하는가?
- 후보가 변경되면 다시 승인해야 하는 이유를 납득하는가?

### 승인과 확정

- 각자 자신의 계정으로 승인해야 최종 확정된다는 규칙을 이해하는가?
- 한 명만 승인한 상태와 양측 승인 완료 상태를 구분할 수 있는가?
- 중복 승인과 확정 후 재승인이 차단됐을 때 이유를 이해하는가?
- 결정 완료까지 걸리는 단계가 지나치게 많지 않은가?

### 기록과 확장 기능

- 결정 기록 기능이 실제로 다시 보고 싶은 정보인가?
- 기록에서 제목, 후보, 조건 요약, 확정 시각 중 어떤 정보가 필요한가?
- OUR PET이 공동결정 경험을 재미있게 만드는가?
- 경험치 보상이 공동결정을 반복해서 사용할 동기가 되는가?
- PET DOCK이 없어도 웹서비스만으로 충분히 사용할 수 있는가?
- PET DOCK이 있을 때 장치 연결 과정이 핵심 흐름을 방해하지 않는가?
- 일정·알림 기능이 공동결정 이후의 행동에 실제 도움이 되는가?

### 검증 시 수집할 정보 예시

- 단계별 완료 여부와 이탈 지점
- 각 단계의 소요 시간과 도움 요청 횟수
- 초대 코드, current 후보, 독립 승인, confirmed 상태에 대한 이해
- 비공개 조건 입력 전후의 부담감과 신뢰 이유
- 결정 기록 재조회 의향
- 하드웨어 유무에 따른 핵심 흐름 완료 차이

위 항목도 조사 계획 예시이며 아직 수집된 결과가 아니다.

## 7. 완료 판정

### 구분 결과

| 구분 | 이 문서의 내용 | 검증 상태 |
|---|---|---|
| 현재 확정된 서비스 타깃 | 반복적인 공동결정 상황을 갖는 연인·부부 | 프로젝트 기획 범위로 확정, 실제 시장 검증 전 |
| 가상 페르소나 | 조건과 탐색 역할이 다를 수 있는 가상 사용자 A/B 한 쌍 | 가상 시나리오, 실존 인물 아님 |
| 기획 단계 문제 가설 | 탐색 부담, 조건 표현 부담, 합의 모호성, 구버전 동의 문제, 기록 가치 | 향후 검증 필요 |
| 실제 사용자 테스트 항목 | 시작·연결·조건·버전·승인·기록·PET·하드웨어 이해와 효용 | 테스트 미실시 |
| 아직 검증되지 않은 내용 | 문제의 빈도, 사용 의향, UI 이해도, 기록·PET·CARE의 실제 가치 | 결과로 단정하지 않음 |

### 자체 검수

- 가상 인물을 `가상 페르소나`로 명시했다.
- 문제 진술을 실제 조사 결과가 아닌 가설로 표시했다.
- 현재 코드 기준 `implemented`, `partial`, `planned`를 분리했다.
- 실제 사용자 테스트에서 확인할 질문을 별도 `향후 검증` 섹션으로 분리했다.
- 아직 사용자 테스트 결과를 작성하지 않았다.

따라서 WBS 1.1.2 완료 기준인 **“가상 페르소나와 실제 검증할 가설이 구분됨”을 충족**한다. 이 판정은 기획 산출물의 완료이며 사용자 문제나 서비스 효과가 실제로 검증됐다는 뜻은 아니다.
