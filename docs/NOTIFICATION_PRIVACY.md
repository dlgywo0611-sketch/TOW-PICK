- WBS: 1.2.8
- 작업명: n8n 알림 동의·개인정보 전송 범위 설계
- 담당자: 이효재
- 작성일: 2026-11-24
- 우선순위: P1
- 완료 기준: 동의 없는 알림 전송 금지·민감 조건 미전송 원칙 확정
- 구현 상태: **partial** (2026-11-25 2차 백엔드: 일정·동의·작업 원장 기반; 실제 발송 planned)

## 문서 범위와 현재 상태

이 문서는 OURVERSE 3.0의 SMART COUPLE CARE에서 기념일 또는 일정 등록 후 n8n을 통해 알림을 발송하기 위한 설계 원칙을 정의한다.

현재 저장소에는 일정 모델·API, 사용자별 알림 동의 API, 미발송 작업 원장이 있다. 실제 n8n workflow, Gmail 발송, 발송 결과·재시도 worker는 아직 없다. 아래 원칙 중 실제 계약은 `API_CONTRACT.md`의 2026-11-25 2차 백엔드 계약을 따른다.

프론트엔드와 n8n은 `API_CONTRACT.md`에 없는 발송 endpoint나 schema를 임의로 가정하지 않는다. n8n 연결과 실제 전송 전에는 인증·재시도·결과 기록 계약을 별도로 확정해야 한다.

## 1. 알림 목적과 범위

### planned 알림

- 사용자가 등록한 기념일 또는 일정의 D-1 알림
- 사용자가 등록한 기념일 또는 일정의 당일 알림
- 사용자가 명시적으로 동의한 채널과 수신 대상에 대한 알림
- 테스트 환경에서 동의한 테스트 계정으로 보내는 검증 알림

### 범위 원칙

- 알림은 일정 리마인드 목적에만 사용한다.
- 일정 등록 사실이 곧 알림 동의를 의미하지 않는다.
- 커플 연결 사실이 곧 이메일 또는 다른 채널 수신 동의를 의미하지 않는다.
- 사용자가 선택하지 않은 D-1·당일 알림을 자동으로 활성화하지 않는다.
- 테스트 환경에서는 실제 사용자 주소가 아닌 명시적으로 동의한 테스트 계정을 우선 사용한다.
- 광고, 추천, 커뮤니티 또는 다른 목적의 메시지는 이 동의 범위에 포함하지 않는다.

## 2. 사용자 동의 규칙

### 기본 규칙

1. 알림 동의 기본값은 `false`다.
2. 사용자별 명시적 동의 후에만 해당 사용자에게 발송한다.
3. 동의 화면은 알림 목적, 채널, 수신 정보, D-1/당일 종류와 철회 방법을 보여줘야 한다.
4. 사용자는 자신의 현재 동의 여부와 동의 시각을 확인할 수 있어야 한다.
5. 동의 철회 후 생성되는 알림과 아직 발송되지 않은 기존 알림 작업을 차단한다.
6. 커플 중 한 명의 동의를 상대방의 동의로 복사하거나 추정하지 않는다.
7. 이메일 주소 보유, 커플 가입, 일정 공유 또는 과거 발송 성공을 동의로 간주하지 않는다.

### 사용자별 독립 동의

| 사용자 A | 사용자 B | A에게 발송 | B에게 발송 |
|---|---|---|---|
| 동의 | 동의 | 허용 | 허용 |
| 동의 | 미동의 | 허용 | 금지 |
| 미동의 | 동의 | 금지 | 허용 |
| 미동의 | 미동의 | 금지 | 금지 |

일정이 커플 공유 데이터이더라도 수신 동의는 사용자 개인 단위로 관리한다.

### 동의 기록과 후속 설계

현재 `NotificationSetting`은 사용자별 동의·종류·시각·정책 버전을 저장한다. 아래의 별도 채널별 동의 등은 아직 설계 제안이며 실제 필드와 계약이 없다.

| 항목 | 목적 |
|---|---|
| 사용자 식별자 | 동의 주체 구분 |
| 알림 목적 | 일정 리마인드 등 목적 제한 |
| 채널 | 이메일 등 수신 채널 구분 |
| 동의 여부 | 현재 발송 허용 여부 |
| 동의 시각 | 명시적 동의 이력 |
| 철회 시각 | 철회 이후 발송 차단과 감사 기록 |
| 정책 버전 | 어떤 안내에 동의했는지 확인 |

동의 상태 변경은 인증된 본인만 수행하며, 클라이언트가 다른 사용자의 ID를 보내 상대 동의를 바꿀 수 없어야 한다.

### 이중 동의 확인

동의는 다음 두 시점에 모두 확인한다.

1. 알림 작업을 만들거나 예약할 때
2. n8n으로 최소 payload를 전달하기 직전

첫 확인 후 사용자가 철회할 수 있으므로 발송 직전 재확인을 생략하지 않는다. n8n 또는 프론트엔드가 동의 여부를 자체 추정하지 않고 백엔드의 최신 동의 상태를 기준으로 한다.

## 3. 개인정보 최소 전송 원칙

### n8n 전달 허용 데이터 — 설계 제안 (`planned`)

| 데이터 | 허용 조건 | 로그 원칙 |
|---|---|---|
| 알림 작업 식별자 | 실행 결과를 동일 작업에 연결할 때 | 내부 opaque ID만 기록 |
| 일정 식별자 | 발송 결과와 원 일정 연결에 필요할 때 | 일정 상세 전체를 함께 남기지 않음 |
| 알림 유형 | `D-1` 또는 `당일` | 허용 |
| 발송 예정 시각 | 실행 예약에 필요 | timezone 포함 |
| 수신 대상 내부 식별자 | 결과 귀속과 중복 방지에 필요 | 외부 로그 노출 최소화 |
| 수신 이메일 등 전달 주소 | 실제 발송에 꼭 필요하고 사용자가 동의한 경우 | n8n 로그에서 마스킹, 장기 보관 금지 |
| 최소 알림 문구 | 사용자가 기대하는 일정 리마인드에 필요한 경우 | 비공개 조건 포함 금지 |
| 중복 방지 키 | 동일 알림의 중복 실행 차단 | 허용 |

백엔드가 최종 제목·본문을 생성한 뒤 n8n에는 발송에 필요한 최소 메시지만 전달하는 방식을 우선한다. 가능하면 “등록한 일정이 내일입니다”처럼 일반 문구를 사용하고, 일정 제목을 포함할 경우 사용자가 입력한 제목이 수신 메시지에 노출됨을 사전에 안내한다.

### 전송 금지 또는 제한 데이터

다음 정보는 n8n 알림 payload에 포함하지 않는다.

- 비밀번호 또는 password hash
- JWT와 refresh token
- `SECRET_KEY`
- n8n API key, Webhook secret, Gmail credential
- 사용자별 비공개 취향, 예산, 시간 조건 등 TWO-PICK 개인 조건
- 불필요한 커플 대화 내용과 Message 전체
- Couple 또는 User 객체 전체
- 상대방의 이메일이나 동의 상태처럼 해당 수신에 필요하지 않은 정보
- 초대 코드
- 결정 후보·승인 이력 전체
- 기타 알림 발송에 필요하지 않은 개인정보

### 최소 수집·보관 원칙

- backend DB를 일정과 동의의 기준 저장소로 두고 n8n에는 필요한 실행 payload만 전달한다.
- n8n execution log에는 메시지 본문과 수신 주소 원문을 가능하면 남기지 않는다.
- 성공한 작업은 장기 보관이 필요한 최소 결과만 backend 원장에 남긴다.
- 실패 분석 로그도 비밀정보와 개인 조건을 제거한 상태로 저장한다.
- 실제 보관 기간은 구현 전에 운영 정책으로 정하고 무기한 보관을 기본값으로 두지 않는다.

## 4. n8n 데이터 흐름

### 권장 흐름 (예약 기반 partial, 발송 planned)

```text
인증된 사용자가 기념일/일정 등록
  → backend가 현재 커플 권한 확인
  → backend DB에 일정 저장
  → 사용자별 알림 종류와 동의 상태 확인
  → 동의한 사용자에 대해서만 발송 대상·예정 시각 계산
  → 중복 방지 키를 가진 알림 작업 생성
  → 발송 직전 일정 상태·동의·수신 정보 재확인
  → 허용 데이터만 n8n에 전달
  → n8n이 Gmail 또는 테스트 메일로 발송
  → 성공·실패 결과를 backend 알림 원장에 기록
```

### 동의 우회 방지

- 프론트엔드가 n8n Webhook을 직접 호출하지 않는다.
- n8n은 클라이언트가 보낸 `consented=true` 값을 신뢰하지 않는다.
- backend가 인증 사용자와 DB의 최신 동의 상태를 확인한 뒤 작업을 생성한다.
- 발송 직전 backend 또는 승인된 발송 단계가 동의를 다시 확인한다.
- 동의가 없거나 철회된 경우 n8n에 수신 정보와 메시지를 전달하지 않는다.
- n8n Webhook은 인증, 서명 또는 네트워크 제한 등 승인된 호출만 허용하도록 설계한다.
- 다른 커플의 일정 ID로 작업을 만들거나 결과를 조회할 수 없도록 `couple_id` 권한을 확인한다.

### 책임 분리

| 구성요소 | 책임 | 금지 사항 |
|---|---|---|
| 프론트엔드 | 일정·알림 선택 UI, 동의·철회 요청 | 직접 n8n 발송, 상대방 동의 변경 |
| backend | 인증·커플 권한, 일정·동의 기준 데이터, 예약·중복 키, 최소 payload 생성 | 민감 조건 전달, 동의 없는 작업 생성 |
| n8n | 승인된 작업 실행, Gmail 호출, 결과 반환 | 동의 추정, 전체 User/Couple 데이터 조회 |
| Gmail/테스트 메일 | 지정된 수신 주소로 메시지 전달 | OURVERSE 내부 데이터 직접 접근 |

## 5. 중복 발송 방지

### 중복 방지 키

동일한 일정의 동일 수신자에게 같은 종류의 알림이 여러 번 전송되지 않도록 다음 요소를 조합한 idempotency key를 사용한다.

- 일정 ID
- 일정 revision 또는 변경 버전
- 수신 대상 사용자 식별자
- 알림 종류: `D-1` 또는 `당일`
- 발송 대상의 `Asia/Seoul` 기준 날짜

설계 예:

```text
dedupe_key = hash(
  schedule_id
  + schedule_revision
  + recipient_user_id
  + notification_type
  + target_local_date
)
```

현재 백엔드는 위 요소를 `:`로 이어 SHA-256으로 해시하여 `dedupe_key` unique 컬럼에 저장한다. 이는 **중복 예약 방지**까지 구현한 것이다. 여러 scheduler 또는 n8n 실행의 원자적 claim·중복 발송 방지는 아직 구현하지 않았다.

### 발송 원장 상태 (현재 pending/canceled, 발송 상태 전이 planned)

| 상태 | 의미 |
|---|---|
| `pending` | 발송 예정 |
| `processing` | 한 실행자가 작업을 선점함 |
| `sent` | 메일 provider 성공 응답과 발송 시각 기록 |
| `failed` | 시도했으나 실패, 오류 종류와 횟수 기록 |
| `canceled` | 동의 철회, 일정 삭제·변경 등으로 발송 금지 |
| `skipped` | 동의 없음, 수신 주소 없음 등으로 실행하지 않음 |

최소 기록 항목:

- 일정 ID와 revision
- 수신 대상 식별자
- 알림 종류
- 중복 방지 키
- 발송 예정 시각과 timezone
- 현재 상태
- 시도 횟수
- 최종 성공·실패 시각
- provider message ID가 있다면 최소 식별자
- 민감정보를 제거한 오류 코드

### 재시도 원칙

- 재시도는 새 dedupe key를 만들지 않고 같은 알림 작업의 시도 횟수를 증가시킨다.
- 일시적 n8n/Gmail 오류에만 제한된 횟수와 backoff로 재시도한다.
- 동의 철회, 일정 삭제, 수신 주소 없음은 재시도하지 않고 `canceled` 또는 `skipped`로 종료한다.
- timeout으로 발송 성공 여부가 불명확하면 provider 결과나 message ID를 확인하기 전 새 메일을 보내지 않는다.
- 최대 재시도 횟수를 넘으면 `failed`로 유지하고 운영 확인 대상으로 남긴다.
- 여러 실행자가 같은 pending 작업을 동시에 가져가지 않도록 DB transaction 또는 atomic claim을 사용한다.

## 6. 시간대 기준

- 한국 사용자 기준 timezone은 IANA 식별자 `Asia/Seoul`을 사용한다.
- 현재 일정 원본은 한국 현지 `local_date`와 선택 `local_time`으로 저장하고 API 응답에서 `Asia/Seoul`을 명시한다. 예정 작업 `send_at`은 UTC 시각으로 저장한다. 운영 환경에는 IANA timezone 데이터가 필요하며 Windows 개발 환경에서 데이터가 없으면 현대 한국 날짜에 한해 UTC+09:00으로 대체 계산한다.
- D-1은 `Asia/Seoul`의 일정 날짜에서 calendar date 1일을 뺀 날짜다. 단순히 24시간을 빼는 방식으로 정의하지 않는다.
- 당일 알림은 `Asia/Seoul`의 일정 날짜와 발송 날짜가 같은지 기준으로 한다.
- 날짜 경계 판단은 backend에서 한 번 계산하고 n8n이 서로 다른 timezone으로 다시 해석하지 않도록 한다.
- 백엔드 기본 발송 시각은 오전 9시 KST이며 사용자별 현지 시각 입력으로 바꿀 수 있다. 현재는 다음 반복 발생일의 미발송 작업만 예약한다.
- 일정 시각 변경 시 revision을 증가시키고 이전 pending 작업을 취소한 뒤 새 시각으로 작업을 만든다.
- 날짜·시각 테스트에는 23:59, 00:00, 월말, 연말, 윤년과 D-1 경계를 포함한다.

## 7. 실패 및 예외 처리

| 상황 | 처리 원칙 | 기록 상태 | 사용자/운영 후속 |
|---|---|---|---|
| 알림 미동의 | 작업을 만들지 않거나 발송 전에 중단, n8n에 수신 정보 미전달 | `skipped_no_consent` 또는 작업 없음 | 동의를 강요하지 않고 현재 상태 표시 |
| 동의 철회 | 모든 미발송 작업 취소, 발송 직전 재확인에서 차단 | `canceled_consent_withdrawn` | 철회 완료와 이후 미발송 안내 |
| 수신 주소 없음 | 발송하지 않음 | `skipped_no_recipient` | 수신 정보 설정 안내 |
| 일정 삭제 | 연결된 pending 작업 취소 | `canceled_schedule_deleted` | 삭제된 일정 알림 미발송 |
| 일정 시간 변경 | 기존 revision 작업 취소, 새 revision과 dedupe key 생성 | 기존 `canceled`, 신규 `pending` | 변경된 예정 시각 표시 |
| n8n 실행 실패 | 같은 작업으로 제한적 재시도 | `failed` 또는 재시도 중 | 운영 로그와 재시도 횟수 확인 |
| Gmail 발송 실패 | 오류 유형에 따라 제한적 재시도 | `failed` | 주소 오류·인증 오류 구분, 민감 로그 금지 |
| 동일 이벤트 중복 실행 | unique key로 기존 작업 재사용, 새 발송 금지 | 기존 상태 유지 | 중복 trigger 횟수 기록 가능 |
| 발송 결과 불명확 | provider 확인 전 중복 재발송 금지 | `processing` 또는 별도 unknown 사유 | 운영 확인 후 동일 작업 재개 |
| 다른 커플 일정 접근 | 일정·알림 정보 미노출 | 작업 생성 없음 | 403 정책 적용 검토 |

현재 내부 원장의 상태명은 `pending`, `canceled`다. 위 세부 예외 값은 향후 발송 worker 설계 제안이며 현재 API 응답값이 아니다.

## 8. 개인정보 및 보안

### 테스트와 자격 증명

- 테스트는 명시적으로 동의한 테스트 계정을 우선 사용한다.
- n8n API key, Webhook secret과 Gmail credential은 n8n credential store 또는 승인된 secret 저장소에서 관리한다.
- 자격 증명을 Git, 문서, payload, 실행 로그 또는 화면 캡처에 포함하지 않는다.
- 테스트 증빙의 이메일 주소, message ID와 개인 내용은 마스킹한다.

### 로그와 보관

- n8n 실행 로그에 JWT, 비밀번호, 비공개 조건, 전체 이메일 주소와 전체 메시지 본문을 남기지 않는다.
- payload preview와 오류 로그에 redaction을 적용한다.
- 실행 결과는 작업 ID, 상태, 시각, 오류 코드 등 최소 감사 정보만 장기 보관한다.
- 원본 payload와 provider 응답은 필요한 기간만 보관하고 자동 삭제 정책을 둔다.
- 실제 보관 기간과 삭제 절차는 구현 전에 개인정보 운영 정책으로 승인한다.

### 커플 데이터 격리

- 일정과 알림 작업의 소유권은 `current_user.couple_id`로 검증한다.
- 생성자 ID만으로 다른 커플 데이터 접근을 허용하지 않는다.
- 사용자는 자신의 동의와 수신 정보만 조회·변경할 수 있다.
- 상대방 동의 여부는 발송 제어에 필요한 최소 상태만 노출하고 상세 수신 정보를 반환하지 않는다.
- n8n callback도 작업 ID와 backend 검증을 통해 원래 커플 작업에만 결과를 기록한다.
