- 현재 저장소의 기획·기능·API·구조·DB·테스트 문서

- 기본 캐릭터 풀은 곰과 토끼 총 2종이다.
- 하나의 Couple은 펫 한 마리만 보유한다.
- 커플 연결 후 두 사용자가 각자 자신의 생일 월·일을 입력한다.

- 덧셈 기반 규칙이므로 사용자 A/B의 입력 순서를 바꿔도 결과가 같다.
- 생년은 필요하지 않으며 수집하지 않는다.

- 각자의 생일 월·일은 상대방에게 자동 공개하지 않는다.
- 가능한 경우 정확한 생일 대신 최종 `species`와 배정 규칙 버전만 영속 저장한다.

## 3. OUR PET 핵심 콘셉트

OUR PET은 두 사용자가 TWO-PICK으로 함께 결정한 경험을 시각적으로 축적하는 **커플 공동 성장 펫**이다.

### 핵심 원칙

- 펫은 사용자 개인이 아니라 Couple에 하나만 존재한다.
- 캐릭터 풀은 곰과 토끼 2종이며 각 커플에는 그중 한 마리만 배정한다.
- 두 사용자는 같은 펫 상태와 성장 결과를 본다.
- TWO-PICK Decision이 정상적으로 `confirmed`될 때 성장 경험이 발생한다.
- 동일 Decision으로 경험치를 두 번 지급하지 않는다.
- 펫은 공동 활동의 결과를 표현하지만 공동결정 승인 주체가 아니다.
- 하드웨어가 없어도 펫과 TWO-PICK 웹 흐름은 동작해야 한다.
- 캐릭터 외형보다 공동결정과 성장의 연결을 우선한다.

### 사용자 가치 가설

- 공동결정 완료를 단순 상태 변경보다 즐겁게 느낄 수 있다.
- 두 사람이 함께 쌓은 결정 기록을 성장 상태로 확인할 수 있다.
- 반복 사용 동기를 높일 가능성이 있다.

위 가치는 아직 실제 사용자 테스트로 검증되지 않은 기획 가설이다.

### 생일 조합 배정 규칙 (`planned`)

각 사용자가 자신의 생일에서 월과 일만 입력한다. 생년은 입력 필드와 저장 구조에 포함하지 않는다.

```text
total = month_a + day_a + month_b + day_b

total이 짝수 → bear
total이 홀수 → rabbit
```

예:

- A `03/14`, B `07/22`: `3 + 14 + 7 + 22 = 46` → 곰
- A `03/14`, B `07/21`: `3 + 14 + 7 + 21 = 45` → 토끼
- A/B 순서를 바꿔도 같은 숫자를 더하므로 결과는 변하지 않는다.

입력은 월 1~12와 해당 월에 가능한 일자로 검증하고 2월 29일도 유효한 생일 입력으로 처리해야 한다. 이 규칙은 게임적 개인화를 위한 결정적 배정이며 궁합, 성격, 관계 적합성 또는 과학적 분석을 의미하지 않는다.

### 생일 최소 수집 설계 (`planned`)

권장 방식:

1. 인증된 각 사용자가 자신의 월·일만 제출한다.
2. backend는 요청 시 유효성을 검사하고 `(month + day) % 2`의 parity만 임시 기여값으로 저장한다.
3. 같은 Couple의 서로 다른 두 사용자 기여값이 모이면 합계 parity로 곰·토끼를 배정한다.
4. 배정 후 임시 기여값을 삭제하고 Couple의 `species`와 `assignment_rule_version`만 영속 저장한다.
5. 생일 월·일 원문과 생년은 펫 배정 데이터로 영속 저장하지 않는다.

정확한 월·일을 일정·CARE 기능에도 사용하려면 펫 배정과 별개의 목적·동의·API 계약이 필요하다. 펫 배정 입력을 기념일 알림에 자동으로 재사용하지 않는다.

곰·토끼 2종 중 커플당 한 마리를 배정하되, 두 종 모두 기본·성장 상태를 준비한다.

| 기능 | P1 최소 범위 | 완료 조건 |
|---|---|---|
| 캐릭터 풀 | 곰·토끼 총 2종, 커플당 한 마리 | 순서와 무관한 생일 조합 규칙으로 한 종만 배정 |
| 상태 이미지 | 곰 기본·성장, 토끼 기본·성장 총 4장 | 배정된 종의 기본·성장 상태를 화면에서 구분 가능 |
| 최소 수집 | 생년 미수집, 생일 원문 비영속 권장 | 배정 후 species·규칙 버전만 영속 저장 |
| 경험치 표시 | 현재 경험치와 성장 진행 상태 표시 | backend 응답과 UI 값 일치 |
| 레벨 표시 | 현재 성장 단계 또는 레벨 표시 | 확정된 규칙에 따라 상태가 일관되게 변경 |
| 결정 연동 | Decision 확정 후 펫 상태 갱신 | 동일 Decision 재처리에도 경험치 1회만 지급 |
| 버튼 반응 | PET DOCK A/B 입력에 간단한 시각 반응 | 승인 API 호출 없이 짧은 반응 표시 |
| LED 연동 | 펫 상태를 R/G/B/X 중 확정된 명령으로 표현 | 웹 표시와 실제 LED 결과 일치 |
| 장치 독립성 | 장치 미연결 상태에서도 펫 화면 사용 | TWO-PICK·펫 조회 흐름이 중단되지 않음 |

### 권장 구현 우선순위

1. 사용자별 생일 parity 기여와 Couple별 species 배정 설계
2. Couple별 PetState와 경험치 원장 설계·구현
3. 결정 확정과 경험치 1회 지급의 원자적 처리
4. 곰·토끼 기본·성장 상태 4개 승인 에셋 연결
5. 경험치·레벨·상태 UI 표시
6. PET DOCK 버튼 반응과 LED 상태 연결

경험치 지급량, 레벨 threshold와 정확한 색상 매핑은 팀 승인 전 임의 값으로 확정하지 않는다. 개발 중 임시 값이 필요하면 테스트 fixture 또는 명시적인 placeholder로만 사용하고 기획 확정값으로 문서화하지 않는다.

## 6. TWO-PICK과 경험치 연계 원칙

### 지급 조건

- 로그인한 두 커플 사용자가 동일한 최신 Candidate를 각각 승인한다.
- backend가 Decision을 `confirmed`로 전환한다.
- 이 확정 이벤트에 연결된 경험치 원장 행을 한 번만 만든다.
- 원장 행 생성이 성공한 경우에만 Couple의 PetState를 갱신한다.

### 중복 지급 방지

DB 수준에서 최소 다음 의미의 unique constraint를 사용한다.

```text
UNIQUE(couple_id, event_type, source_decision_id)
```

- `event_type`은 공동결정 확정 경험치임을 구분한다.
- `source_decision_id`는 지급 원인이 된 정확한 Decision을 고정한다.
- API 재시도, 페이지 새로고침 또는 중복 callback이 새 경험치를 만들지 않는다.
- 프론트엔드의 중복 클릭 방지는 보조 수단이며 DB unique를 대체하지 않는다.
- 확정 상태 전이, 최종 결정 기록, 경험치 원장과 PetState 갱신은 가능한 한 하나의 transaction에서 처리한다.

### 소유권과 권한

- PetState의 소유자는 `user_id`가 아니라 `couple_id`다.
- 두 구성원은 같은 펫을 조회한다.
- 다른 커플의 펫 상태와 경험치 원장을 조회·변경할 수 없다.
- 클라이언트가 보낸 `couple_id`를 권한 근거로 신뢰하지 않는다.

### 미확정 규칙

- 결정당 경험치 양
- 시작 경험치와 최대값
- 성장 단계 수와 threshold
- 확정 취소 또는 데이터 정정 시 경험치 처리
- 수동 경험치 지급 권한

위 값은 현재 팀 승인 근거가 없어 구현 전 별도 계약이 필요하다.

## 7. PET DOCK과의 관계

### 역할

- Arduino UNO 버튼 A/B는 USB Serial 9600 baud와 Browser Web Serial을 통해 PET 반응 이벤트로 사용한다.
- Browser는 KEYES `Meem`의 FFE0/FFE1에 R/G/B/X를 WRITE해 RGB LED 상태를 제어할 수 있다.
- 펫 상태에 따른 LED 의미는 최종 매핑 승인 후 연결한다.
- 버튼 반응은 bounce, blink, 표정 변경 같은 짧은 시각 반응 중 최소안으로 구현할 수 있다.

### 승인 경계

- PET DOCK 버튼은 공동결정 승인 버튼이 아니다.
- 버튼 handler는 `/candidates/{candidate_id}/approve`를 호출하지 않는다.
- 하드웨어 이벤트는 DecisionApproval을 생성하지 않는다.
- 공동결정 승인은 로그인한 두 사용자가 웹에서 각각 수행한다.
- 장치가 연결되지 않아도 TWO-PICK 승인과 펫 상태 조회가 가능해야 한다.

### 현재 상태

- USB 버튼, Web Serial, Meem 연결, R/G/B/X LED 제어는 성주연의 2026-11-23 실물 반복 시험에서 성공했다.
- 정식 증빙 파일 또는 팀 공유 링크 등록은 아직 미완료다.
- Web Serial/Web Bluetooth bridge는 현재 `main`에 통합되지 않았다.
- BLE Notify 버튼 경로는 미구현이다.
- PET 상태와 LED의 실제 연동은 planned / NOT TESTED다.

## 8. 화면 및 에셋 제작 요구사항

### A. 이미지 에셋 기반 최소안 — P1 권장

현재 HTML/CSS/JS 구조에서 가장 작은 구현 범위다.

- 투명 배경의 PNG, WebP 또는 프로젝트가 선택한 web-safe image format
- 곰 기본 1장, 곰 성장 1장, 토끼 기본 1장, 토끼 성장 1장
- 네 파일 모두 동일한 canvas, 중심점과 표시 비율 사용
- species와 상태를 함께 식별할 수 있는 일관된 파일명 사용
- CSS class 전환 또는 image source 변경으로 상태 표현
- 버튼 이벤트는 CSS transform/opacity 또는 짧은 frame 교체로 반응
- 경험치 bar, level text와 상태명은 HTML로 제공
- 색상만으로 상태를 구분하지 않고 text·shape를 함께 사용
- `prefers-reduced-motion` 사용자를 위한 정적 대체 상태 제공
- 모바일·데스크톱에서 잘리지 않는 responsive container 사용

에셋 전달 시 필요한 항목:

- 승인 시안과 승인자·승인일
- 원본 파일과 web export 파일
- 곰·토끼의 기본·성장 상태 매핑표
- 배경 투명도, canvas 크기, 중심점 규칙
- 사용 권한과 출처
- 에셋 version과 변경 이력

### B. Blender 에셋 사용 조건 — P2 또는 조건부 보류

Blender 사용은 다음 조건을 충족할 때만 검토한다.

- 실제 `.blend` 원본과 texture가 팀 저장소 또는 공유 저장소에 확보됨
- 저작권·라이선스와 수정 권한이 확인됨
- web export용 GLB/glTF 또는 렌더 이미지 pipeline이 재현 가능함
- 모델 polygon, texture 용량과 초기 loading 시간이 P1 일정에 적합함
- 기본·성장 상태와 필요한 animation이 실제로 준비됨
- 브라우저 호환성과 저사양 기기 성능을 검증함
- 3D 실패 시 사용할 2D fallback이 있음

현재는 위 조건을 확인할 파일이 없으므로 Blender 모델을 확보했거나 P1에서 사용할 수 있다고 표시하지 않는다.

### 에셋 미제작 기간의 개발 원칙

- 중립 placeholder는 layout 개발에만 사용한다.
- placeholder를 최종 캐릭터로 발표하지 않는다.
- `bear`와 `rabbit`은 이번 기획에서 허용된 두 species 값으로 사용한다.
- 월·일 합의 홀짝 규칙은 버전 식별자를 함께 저장해 이후 규칙 변경을 추적한다.
- 실제 시안 승인 후 에셋, UI와 발표 자료의 외형을 정합화한다.

### WBS 최종 완료 판정

이번 기획 변경으로 곰·토끼 2종, 커플당 한 마리, 생일 월·일 합의 홀짝 배정, 생년 미수집, 입력 순서 독립성, 최소 수집 원칙과 P1 에셋 범위를 확정했다. 따라서 **WBS 1.1.5 기획은 완료**로 판정한다.

다만 다음 항목은 구현 완료가 아니다.

- 곰·토끼 기본·성장 이미지 4장 제작과 권리 확인
- PetState·배정 API·경험치 원장 구현
- 배정·privacy·중복 경험치 자동 테스트
- PET DOCK 반응과 LED 상태 통합

색상·세부 외형·경험치 수치는 후속 디자인·기술 계약에서 확정한다. WBS 기획 완료를 OUR PET 구현 또는 사용자 가치 검증 완료로 표시하지 않는다.
